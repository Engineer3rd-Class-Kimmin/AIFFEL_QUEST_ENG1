## 섹션 2. async/await의 기본 원리

### Q1. `time.sleep(3)`과 `await asyncio.sleep(3)`의 핵심 차이는 무엇입니까?

`time.sleep(3)`은 실행 중인 스레드를 3초 동안 멈추기 때문에
그동안 다른 작업을 처리할 수 없습니다.

`await asyncio.sleep(3)`은 기다리는 동안 이벤트 루프에 실행 권한을 넘겨주므로
다른 작업을 처리할 수 있습니다.

### Q2. 모델 추론처럼 CPU를 계속 사용하는 작업에서 `async/await`만으로 동시 처리가 안 되는 이유는 무엇입니까?

`async/await`은 네트워크 요청이나 파일 입출력처럼
대기 시간이 발생하는 I/O 작업에 효과적입니다.

모델 추론처럼 CPU를 계속 사용하는 작업은 이벤트 루프를 계속 점유하기 때문에
`async/await`만으로는 동시 처리가 어렵습니다.

## 섹션 3. 문제 시연: 동기 추론이 서버를 멈추는 순간

### Q1. `async def` 안에서 `time.sleep(3)`을 호출하면 왜 다른 요청까지 지연됩니까?

`time.sleep(3)`이 이벤트 루프가 실행되는 스레드를 멈추기 때문입니다.

따라서 같은 이벤트 루프에서 처리해야 하는 다른 요청도 함께 지연됩니다.

### Q2. 일반 `def`로 선언된 엔드포인트는 FastAPI가 내부적으로 어떻게 처리합니까?

FastAPI는 일반 `def` 엔드포인트를
내부 스레드풀(Thread Pool)에서 실행합니다.

따라서 동기 함수가 실행되더라도
메인 이벤트 루프가 직접 블로킹되는 것을 방지합니다.

### Q3. blocking 추론 중 헬스체크까지 막히면 실무에서 어떤 문제가 발생할 수 있습니까?

헬스체크가 실패하면 Docker, Kubernetes, 로드밸런서 등이
서버를 비정상 상태로 판단할 수 있습니다.

그 결과 서버가 재시작되거나 트래픽에서 제외되어
서비스 장애로 이어질 수 있습니다.

## 섹션 4. 해결 패턴: run_in_executor로 블로킹 방지하기

### Q1. `run_in_executor`가 이벤트 루프 블로킹을 방지하는 원리는 무엇입니까?

블로킹 작업을 이벤트 루프에서 직접 실행하지 않고
별도의 스레드풀에 전달하여 실행합니다.

따라서 이벤트 루프는 다른 요청을 계속 처리할 수 있습니다.

### Q2. `run_in_executor`의 첫 번째 인자에 `None`을 넣으면 어떤 스레드풀이 사용됩니까?

이벤트 루프가 사용하는 기본 `ThreadPoolExecutor`가 사용됩니다.

### Q3. 일반 `def`와 `async def + run_in_executor`의 핵심 차이는 무엇입니까?

일반 `def`는 FastAPI가 자동으로 스레드풀에서 실행합니다.

반면 `async def + run_in_executor`는 개발자가 특정 블로킹 작업을
직접 스레드풀에 전달하여 실행할 수 있습니다.

### Q4. GPU 추론 시 스레드풀 크기를 1~2로 제한하는 이유는 무엇입니까?

동시에 너무 많은 GPU 추론을 실행하면
GPU 메모리 사용량이 증가하고 성능이 저하될 수 있습니다.

GPU 메모리 부족(OOM)을 방지하기 위해
동시 실행 수를 제한합니다.

## 섹션 5. 에러 핸들링과 로깅

### Q1. 글로벌 Exception Handler를 사용하면 어떤 반복을 줄일 수 있습니까?

각 엔드포인트마다 반복적으로 작성해야 하는
`try-except` 코드와 공통 에러 응답 처리를 줄일 수 있습니다.

### Q2. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는 무엇입니까?

스택 트레이스에는 서버 파일 경로, 코드 구조,
라이브러리 정보 등의 내부 정보가 포함될 수 있습니다.

이러한 정보가 외부에 노출되면
보안상 위험할 수 있습니다.

### Q3. `logging` 모듈이 `print()`보다 나은 점은 무엇입니까?

`logging`은 `INFO`, `WARNING`, `ERROR` 등의 로그 수준을 구분할 수 있으며,
시간과 모듈명 등의 정보를 함께 기록할 수 있습니다.

따라서 실제 서버에서 오류 분석과 상태 추적에 적합합니다.

# 6. Day 3 최종 체크포인트

## Q1. 동기 서버에서 3초 걸리는 추론을 3명이 동시에 요청하면 총 몇 초 걸립니까?

요청이 순차적으로 처리된다면 약 **9초**가 걸립니다.

`3초 × 3명 = 약 9초`

## Q2. `time.sleep(3)`과 `await asyncio.sleep(3)`의 핵심 차이는?

`time.sleep(3)`은 실행 중인 스레드를 멈춥니다.

반면 `await asyncio.sleep(3)`은 대기하는 동안
이벤트 루프에 실행 권한을 넘겨 다른 작업을 처리할 수 있습니다.

## Q3. `async def` 안에서 동기 블로킹 코드를 실행하면 왜 헬스체크까지 영향받습니까?

동기 블로킹 코드가 이벤트 루프를 점유하기 때문입니다.

이벤트 루프가 멈추면 `/predict`뿐만 아니라
`/health`와 같은 다른 API 요청도 처리되지 못합니다.

## Q4. `run_in_executor`가 이벤트 루프 블로킹을 방지하는 원리는?

시간이 오래 걸리는 동기 작업을
별도의 스레드풀에서 실행하기 때문입니다.

이벤트 루프는 그동안 다른 요청을 계속 처리할 수 있습니다.

## Q5. 글로벌 Exception Handler를 사용하는 이유는?

각 엔드포인트에서 반복되는 예외 처리 코드를 줄이고
서버 전체의 오류 응답을 일관되게 관리하기 위해 사용합니다.

## Q6. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는?

스택 트레이스에는 서버 내부 경로, 코드 구조,
라이브러리 정보 등이 포함될 수 있어 보안 위험이 있기 때문입니다.

상세 오류는 서버 로그에 기록하고
클라이언트에게는 안전한 오류 메시지만 반환해야 합니다.
